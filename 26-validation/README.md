# 26. 实战验证：让OCR结果可测量、可复核、可重演

第25章已经能把一张照片变成数字串。本章回答更严格的问题：**它在哪些数据上、用哪个版本、错了多少、错误有没有被完整计入？** 同一条错误预测，排除策略和分母不同，可以得到完全不同的“成绩”。先把测量方法讲清，再讨论优化。

三个主要入口是本讲义、[HTML评估页](index.html)和 [Node.js教学实验](index.js)。HTML承接第25章保存的记录；Node入口提供8个分步实验，不需要先采照片就能理解评分与记录规则。图片生成和批量模型评估是单独的辅助实验。

## 1. 数据划分：独立性发生在增强之前

### 1.1 三个分区回答三个不同问题

训练集用于更新权重，验证集用于选择模型/超参数，最终测试集用于配置冻结后的测量。用符号表示：

```text
θ* = Train(Dtrain, λ)
λ* = Select(Dvalidation)
score = Evaluate(Dtest, θ*, λ*)
```

`θ` 是网络权重向量，`λ` 是学习率、增强、阈值、分割参数等配置；`D` 是带来源标识的样本集合。测试集不参与前两步。数据泄漏不只来自“把测试图片喂给fit”，看过测试错误再改阈值、从多个K里挑测试得分最高的K，也会让测试集承担验证集角色。参见[scikit-learn官方的数据泄漏说明](https://scikit-learn.org/stable/common_pitfalls.html)。

本项目训练报告记录 `seed=1701`、trainSize55,000、validationSize5,000、epochs5、batchSize128、learningRate0.001。训练增强以0.5概率加入±8°旋转和0.9–1.1横向比例变化，每轮重采样；验证和标准测试没有按训练增强随机生成新样本。选择依据是验证交叉熵，最佳轮次5，测试标签用于最终评分。

55,000与5,000来自MNIST官方60,000训练样本的再划分，t10k的10,000仍是官方测试来源。`model/split.json` 保存确切源索引，不能仅凭再次调用同一个随机种子就假定数据版本和划分都相同。

### 1.2 为什么“不同文件”可能是同一个样本

原图P旋转5°得到P1、裁剪字符得到P2、群聊压缩得到P3，它们共享字迹与背景。若P在训练，P1在测试，模型可能只需记住同源特征；这并没有测量新书写者照片。

```text
writerId → sourcePhotoId → 原图/压缩图/旋转图 → 字符裁剪与训练增强
          ↑先在这一层分区，所有下游派生物继承该分区
```

数值示例：一张原图变成4张相似图，再逐图独立按80%/20%分训练/测试。已知其中一张在测试，其余3张至少一张进训练的概率是 `1−0.2³=99.2%`。这是说明机制的随机划分算例，不是本项目的实测泄漏率；它说明“增强后文件数很多”不能增加独立来源数。

工程上应先定义分组函数 `g(sample)`，并要求：

```text
Gtrain ∩ Gvalidation = ∅
Gtrain ∩ Gtest = ∅
Gvalidation ∩ Gtest = ∅
```

G是各分区原图/书写者标识的集合。若有书写者信息，优先以writerId分组；同一人不同照片也可能共享书写风格。没有writerId时至少按原图分组，并明确“书写者隔离无法确认”。分组验证的原则可参考[官方GroupKFold说明](https://scikit-learn.org/stable/modules/cross_validation.html#group-k-fold)，本项目仍用JavaScript清单，不需为此引入Python。

### 1.3 哈希能检查什么，不能检查什么

页面 `imageId` 是导入文件字节的SHA-256，同文件改名后哈希不变，可发现逐字节重复。压缩、转码、旋转会改变字节与哈希，不能据此证明来源独立。应在照片台账补充writerId、sourcePhotoId及派生关系。

MNIST的来源键必须写为 `(sourcePart,sourceIndex)`：`train[3]` 与 `t10k[3]` 不是同一图。夹具清单保存这两个字段。MNIST IDX不提供逐样本书写者ID，本项目遵循官方分区及自己的train/validation索引；不额外宣称已验证每条合成行的书写者隔离。

`validateRecords`校验记录结构与评分所需字段，并拒绝重复id；当imageId和experimentId均非空时，还用二者组成的键拒绝同图同轮重复。它**没有自动检查writerId或训练/测试同源关系**。记录去重和数据科学意义上的独立划分是两个层次，后者需通过来源清单审查。

## 2. 标准数字、合成行、实拍：测试对象不能偷换

### 2.1 三种输入的差异

| 输入 | 自带/缺失的条件 | 经过哪些处理 | 主要误差来源 |
|---|---|---|---|
| MNIST单字 | 28×28，已裁好单个数字 | 归一化→CNN | 字形与分类 |
| MNIST拼接行 | 单字真实，行布局程序生成 | 第25章阈值、分割、归一化、CNN | 合成变换、分割和分类 |
| 手机照片 | 真实纸面、镜头、光照、压缩、方向 | 文件解码→完整pipeline | 前述误差加真实采集差异 |

MNIST官方镜像提供60,000训练和10,000测试样本，并描述IDX格式，见 [CVDF数据来源](https://github.com/cvdfoundation/mnist)。模型使用真实手写数据训练，并不自动意味着“所有照片分布上的真实识别能力”已被测量。

例如一位“4”在标准单字里已完整居中，在照片里却可能因反光断笔，分割后只剩一个像“9”的轮廓。两项任务的输入分布、处理步骤和计分单位不同，97.69%不能直接填到照片整串正确率一栏。

### 2.2 合成夹具到底怎样生成

`prepare-fixtures.js` 使用12个固定字符串：

```text
001208  112233  987654  305  00011  70890
24680   13579   90009   101010  827364  556677
```

总长度为 `6+6+6+3+5+5+5+5+5+6+6+6=64`。开发模式只从第17章 `split.validation` 取源数字；`--test` 模式只从t10k取。各模式内部维护used集合，64个源数字索引不重复；不是拿同一张“0”粘贴十遍。

每个28×28原始数字先反色成白底深色，使用cubic缩放到80×80；第i个数字左边为 `32+88i`，上下位置有−3、0、+3像素交替偏移。未旋转的行画布：

```text
W=88L+64，H=152
L=6 → W=592，H=152
```

80像素图块按88像素间距排布，图块之间留8像素，再叠加各字自身白边。部分行转3°，另一些行加从左到右的线性暗化；`shadow=0.2` 时最右侧乘0.8，白纸255降到约204。该变换模仿一种明暗变化，不等于手机镜头、透视、反光、纸张纹理和群聊压缩的联合分布。

字符串覆盖前导零、连续重复和不同长度，是方便回归的固定例子，不是自然采样的数字串分布。开发与测试共用排版字符串及变换模板，换的是源字迹；这进一步限制测试分数可推广的范围。

### 2.3 怎样呈现当前开发失败与冻结测试

开发报告中 `development-3` 的真值是`987654`，预测是`987659`，6个框、1次替换。该行自身 `CER=1/6≈16.67%`，整组因共有64位，汇总 `CER=1/64=1.5625%`；11行完全一致，整串正确率 `11/12≈91.67%`。

6个框只说明数量相同，不能单凭数量把错误彻底归因到CNN。应查看最后一个框是否夹带背景、归一化是否丢笔、候选是否混淆4/9，再确认是分割、输入处理还是分类问题。当前保存的事实是替换，不是已经完成了病因诊断。

合成测试在读取图片推理前保存冻结记录：Otsu、autoDeskew=true、correctionAngle=0、denoise=false、输入版本 `dark-rgba-bbox20-centroid-v1`，模型标识固定。测试记录的pipelineId为：

```text
9ee08e3a5e4f3e9fe267d4c0c79adbf199caf1db02625b0bb7b578cd43e625cb
```

它是第25章共享引擎文件内容与配置JSON共同生成的SHA-256；对应12行、64位，无S/D/I、12/12整串正确。它是**已经执行的一次小规模合成工程回归**。不能把这些已看过的测试行继续用于选阈值，然后仍把同一组得分称为新模型的未见测试成绩。

测试指纹不覆盖每一个传递依赖、Sharp二进制与浏览器解码器；完整复现还需保存共享代码版本、锁文件、模型、源数据和清单。2026-09-11复核修正了共享旋转和预处理，新运行会在配置中记录 `pipelineVersion: 'ocr-photo-v2-2026-09-11'`，因此上述旧冻结成绩不能直接赋给当前流程。开发报告是在加入冻结字段之前生成的，已有原始预测和配置仍有效；不要为让两个报告结构一致而重跑覆盖或补造早期冻结时间。

## 3. CER的基础：对齐字符，而不是机械对齐下标

### 3.1 为什么一次漏字不应该把后续字符都算错

真值`1203`、预测`123`，下标比较会在第三位把0与3判错，第四位又缺3。实际错误是中间漏掉0，末尾3仍正确。需要允许两串在某处出现空位，寻找最少编辑次数。

本项目采用单位代价Levenshtein距离，方向始终是**真值 → 预测**：

| 操作 | 记号 | 真值到预测的含义 | 代价 |
|---|---|---|---:|
| 匹配 | M | 同一字符 | 0 |
| 替换 | S | 一个真值字符变成另一个预测字符 | 1 |
| 删除 | D | 一个真值字符在预测里消失，即漏字 | 1 |
| 插入 | I | 预测多出真值没有的字符，即多字 | 1 |

### 3.2 动态规划公式、表维度与手算

令真值T长度N、预测P长度M；这里M作为长度符号，与对齐表中操作记号M“匹配”区分。`L[i,j]` 表示真值前i个字符到预测前j个字符的最小编辑数：

```text
L[i,0]=i，L[0,j]=j
L[i,j]=min(
  L[i−1,j−1]+1[T[i−1]≠P[j−1]],  替换或匹配
  L[i−1,j]+1,                    删除
  L[i,j−1]+1                     插入
)
distance=L[N,M]
```

表有 `(N+1)×(M+1)` 项，字符索引从0开始。填表和完整回溯实现的时间/空间都是 `O(NM)`；本课程需要展示具体对齐，所以保留二维表。公共对齐函数上限4,000,000单元格；第26章记录另限制每串最多1000字符、最多2000条记录，避免误导入无界数据。

对Node实验1的`1203 → 123`，表为：

| 真值前缀\预测前缀 | ∅ | 1 | 12 | 123 |
|---|---:|---:|---:|---:|
| ∅ | 0 | 1 | 2 | 3 |
| 1 | 1 | 0 | 1 | 2 |
| 12 | 2 | 1 | 0 | 1 |
| 120 | 3 | 2 | 1 | 1 |
| 1203 | 4 | 3 | 2 | 1 |

例如 `L[3,2]` 将`120`变为`12`：替换路径2，删除路径 `L[2,2]+1=1`，插入路径3，所以取删除。右下 `L[4,3]=L[3,2]+0=1`，最后的3匹配，回溯得到：

```text
真值  1  2  0  3
预测  1  2  ∅  3
操作  M  M  D  M
```

代码对应 `shared/24-post-processing` 的 `alignSequences`；`getEditDistanceTable`可取得同一算法的矩阵。第26章HTML展示回溯结果，完整矩阵教学也可回第24章实验查看。

### 3.3 替换、插入与并列最优路径

补充手算 `123 → 1934`：

```text
真值  1  2  3  ∅
预测  1  9  3  4
操作  M  S  M  I
```

S=1、D=0、I=1，距离2。预测长4而真值长3，这个长度差1并不能解释全部错误，还存在一个替换。

对于`12 → 122`，距离1、插入1。重复的两个2都可与真值2对应，物理上无法仅从文本知道“哪一个2多出来”。本实现从右下回溯，并列时按对角匹配/替换、删除、插入的顺序选择，固定返回：

```text
真值  1  ∅  2
预测  1  2  2
操作  M  I  M
```

再如`12 → 21`，两次替换与一次删一次插同为距离2；本实现返回S=2。编辑距离相同，具体S/D/I构成可能因并列规则不同而变化。比较不同库时先固定代价、方向与回溯规则，不能把对齐缺口的位置当作已经确定的物理错字位置。

## 4. CER与整串完全正确率回答不同问题

### 4.1 单图指标

对于一张有非空答案的有效图片：

```text
CER=(S+D+I)/N
exactMatch=1[truth===prediction]
```

N是**真值字符数**，不是预测长度，也不是正确匹配数。CER越小越好；整串判定只有全对与不全对，不给“几乎正确”半张分数。CER定义可对照[TorchMetrics官方说明](https://lightning.ai/docs/torchmetrics/latest/text/char_error_rate.html)，本项目不依赖该库，直接使用自己的JavaScript对齐实现。

| 真值 | 预测 | S | D | I | CER | 整串正确 |
|---|---|---:|---:|---:|---:|---|
| `1203` | `123` | 0 | 1 | 0 | 1/4=25% | 否 |
| `12` | `122` | 0 | 0 | 1 | 1/2=50% | 否 |
| `123` | `1934` | 1 | 0 | 1 | 2/3≈66.67% | 否 |
| `00110` | `00110` | 0 | 0 | 0 | 0/5=0% | 是 |
| `00110` | `0110` | 0 | 1 | 0 | 1/5=20% | 否 |
| `305` | 空串 | 0 | 3 | 0 | 3/3=100% | 否 |
| `1` | `1111` | 0 | 0 | 3 | 3/1=300% | 否 |

前导零是字符，连续11是两个字符。任何数值转换或去重都会改变目标任务：`Number('00110')`会把5位变成3位，导致分母与比较都错。正确答案必须以字符串保存。

### 4.2 为什么CER可能超过100%

插入次数不受真值长度限制。真值只有`1`，预测`1111`，最短对齐是匹配一个1、插入三个1，因此CER=300%。不要截断成100%；`1−CER=−200%`显然不能作为通用“字符准确率”。只有在固定长度、无插删等特定条件下，补数才有有限解释，本章不用它替代标准单字分类准确率。

当前评分允许预测中有非数字字符，并如实计算编辑；它不会先删除空格、字母或标点让分数变好。真值则严格为非空0–9串，`null/undefined/''`为待标注，不表示“已经确认目标为空串”。如要另做空白检测评估，需要单独定义任务与指标。

### 4.3 micro聚合为什么不能平均逐图CER

设有效样本共K张，第k张编辑数Ek、真值长度Nk、整串正确指示qk：

```text
microCER = (Σk Ek)/(Σk Nk)
exactMatchAccuracy = (Σk qk)/K
```

microCER相当于按真值长度加权逐图CER。Node实验2：A真值`12`预测`12`，E=0、N=2；B真值`1203`预测`123`，E=1、N=4。总体：

```text
CER=1/(2+4)=1/6≈16.67%
整串完全正确率=1/2=50%
逐图CER直接平均=(0+25%)/2=12.5%   ←这是另一种macro口径
```

macro把短串和长串等权，不是数学上不能算，但必须另行命名，不能替代本课程约定的micro。若再加入合法照片C，答案`305`却预测空串，则新增3次删除：`microCER=4/9≈44.44%`，整串1/3≈33.33%。删除失败C只算成功返回的照片，就会虚高成前面的成绩。

实现 `evaluatePredictions` 先累加S/D/I和真值字符总数，最后只除一次；整串按有效样本总数除。没有有效样本时，两种比例都返回 `null`，HTML显示“—”，不返回0、100%或NaN。

### 4.4 指标方法对比

| 方法 | 比较单位 | 能回答的问题 | 本任务的使用方式 |
|---|---|---|---|
| 单数字accuracy | 一个已裁剪数字 | 分类器标签是否正确 | 第17章标准测试 |
| 逐位比较/Hamming式计数 | 同一位置字符 | 对齐已知且长度相同的错误 | 不适合漏字、多字后的整行评分 |
| 编辑距离CER | 真值字符及最少编辑 | 错了多少字符操作 | 第26章主指标，micro聚合 |
| 整串完全正确率 | 一张图片 | 整串是否可直接使用 | 第26章主指标，与CER并列 |
| WER | 空白切分的词 | 词序列错误 | 无空格数字串通常只有一个词，解释力有限 |
| 模型最高得分 | 当前裁剪的分类分布 | 模型偏向哪个类别 | 展示/排障，不能代替正确答案 |

例如同一张50位串只错1位，CER=2%而该图整串正确指示仍为0；一位串错1位，CER=100%但整串同样为0。分享时展示两种指标和原始分子/分母，听众才能知道“读对大部分字符”和“整串可直接使用”的差别。

## 5. 失败、待标注、排除：谁进入分母

### 5.1 先定义输入范围，再观察结果

约定有效输入是白纸深色笔、单行从左到右的0–9数字串，数字有基本间隔、完整入镜；允许轻微倾斜和光照不均。符合这些条件、有正确答案，但模型识别错、拒识或返回空串的照片，仍是有效样本。

损坏文件、没有数字的白纸、明显多行重叠或未拍全的内容，可根据预先说明的范围单记排除理由。不能以“模型分数低”“识别为空”“效果不好”为排除理由，否则是在按模型结果选择容易样本。排除规则应在看预测前确定，尽可能由只看输入的人判定。

代码中的优先级为：

```text
exclusionReason.trim()非空 → excluded
否则 truth为null/undefined/'' → pending
否则 → evaluated
```

`failed`是运行/预测状态，不是上述分组的替代。空预测，或status为failed/error/rejected（大小写不敏感），都会标为失败；**只有已纳入评分的失败行**计入汇总 `failedSamples`。普通非空错误预测仍可能是status=ok，不能把failedSamples当作所有错误照片数。

### 5.2 与Node实验4一致的三条记录

| id | truth | prediction | 状态/理由 | 是否纳入 |
|---|---|---|---|---|
| failed | `305` | `''` | status=failed | 是，3次删除 |
| pending | null | `17` | 无答案 | 否，待标注1 |
| outside-scope | `888` | `8` | 多行重叠，超出单行范围 | 否，排除1 |

输出应为totalSamples3、evaluatedSamples1、totalTruthCharacters3、D=3、CER=1、exactMatchAccuracy=0、pending1、excluded1、failed1。三条输入不意味着分母必须是3；决定分母的是事前范围和答案是否齐备，不能把失败那条移走。

给pending补上答案后会新增一条有效样本，因此比较前后实验时还需检查标注完整度。假设只标了最容易的5张，即使全对，应该写“有答案5张、另有待标注若干”，不能宣称整批照片全对。

### 5.3 页面不能自动覆盖的接收失败

第25章图片读取失败发生在引擎调用前：它会清掉旧输入，显示错误，**不会自动创建一条可保存的照片记录**。本章评估页也没有“新增任意失败文件”的按钮。因此另建接收台账，保留文件名、来源、接收时间和损坏/超范围原因；需要汇入评估时可整理成符合记录格式的JSON导入。

批量 `evaluate-images.js` 对读取/识别异常会保存空预测和error；除非清单已有明确的 `exclusionReason`，合法真值仍进入评分。损坏文件应在检查输入时写明排除理由；不会因抛错就自动排除。清单本身无效、模型加载失败等全局错误则直接终止，不能把未运行批次报告成0%错误。

一个能核对完整性的接收台账应满足：

```text
收到的独立原图数
= 已纳入评分原图数 + 待标注原图数 + 明确排除原图数
```

这条等式按原图计数，不按重试记录数计数。若8张符合范围照片中2张空结果，应保留8张有效照片；若另收到1个损坏文件，共接收9张，另列排除1及理由。此例是流程算例，不是当前已收集照片数量。

## 6. 实验记录：首次结果是证据，重试是新实验

### 6.1 一条记录应能回答什么

| 字段 | 内容与类型 | 用途 |
|---|---|---|
| `id` | 唯一非空字符串 | 逐条记录身份、导入冲突检查 |
| `imageId` | 文件SHA-256等来源标识 | 同一文件的跨轮对照；不是书写者身份 |
| `filename` | 原文件名/清单路径 | 找回输入；JSON本身不包含照片 |
| `experimentId` | 实验轮次字符串 | 区分预演、现场、开发重试 |
| `modelId` | 模型标识 | 追溯具体权重 |
| `pipelineId`、`config` | 流程标识及实际参数 | 比较阈值、倾斜、输入版本 |
| `sampleKind` | `'photo'`、`'synthetic-mnist'`或`'unknown'` | 实拍、合成与未标注来源分别统计 |
| `prediction` | 原始字符串，允许`''` | 推理结果，不被补答案覆盖 |
| `truth` | 0–9字符串或null | 独立答案；保留前导零 |
| `status` | 如ok/failed | 运行状态，不代替exactMatch |
| `exclusionReason` | 空串或明确理由 | 独立于“识别是否好看”的范围判定 |
| `createdAt`、`annotatedAt` | 时间戳，可选 | 保存、补标注时间 |
| `elapsedMs`、`warnings`、`error` | 耗时、警告、失败原因 | 错误定位；部分来源可能缺失 |

照片台账可另加writerId、sourcePhotoId、采集条件与split；这些额外字段可随记录保留，但当前界面不会自动显示或按其分组。浏览器导出不保存原始图片、28×28卡片或完整候选分数，所以复盘时必须同时保存图片；需要中间图证据时在操作时截图并与原图ID对应。

Node图片报告额外保存boxes、实际correctionAngle等字段。早期开发报告没有后续版本新增的experimentId/pipelineId，应诚实显示缺失；无法从缺失字段反推当时的代码哈希。

### 6.2 首次预测和补标注怎样分离

Node实验5先保存prediction=`0010`、truth=null；`annotateRecord`补为truth=`00110`后，prediction仍为`0010`，旧输入数组的truth仍为null。评分变成一次删除、CER=1/5=20%，事实没有被“答案修正”。

浏览器为每次导入的图片保留本轮首次运行对象 `first`，后续尝试更新 `latest`。核对按钮比较latest，保存按钮保存first。因而推荐顺序：

```text
选择轮次 → 导入图片 → 运行一次 → 保存首次结果
                   → 录入/补充答案 → 评分
另做开发对照：新轮次 → 新配置 → 重新运行 → 另存结果
```

答案可以保存时一并录入，也可以稍后在第26章补；关键是先产生预测，且比较函数不改写它。切换轮次会清除first，必须重新运行才能保存。模型/配置改变后，不要仍沿用同一正式测试轮次。

`appendRecord`在已有同 `imageId+experimentId` 时拒绝追加，提示保留首次结果。它并不允许同一轮因换模型而多记同一张；换模型或配置应换轮次。

### 6.3 为什么分组键包含四项

`summarizeExperiments`的分组键是：

```text
[experimentId, modelId, sampleKind, pipelineId]
```

例如照片A在模型1上CER20%，合成行B在模型1上CER0%，模型2又对A试一次CER0%；把3条一起平均，会混合样本来源和版本，还把A当作两张独立照片。应该展示三个实验组，再按共同imageId做开发对照。

Node实验6实际构造3条各有一次删除的记录：模型1实拍、模型1合成、模型2新轮次实拍，返回3组，每组1条、CER0.2。名称为`photo`只是受控记录字段，这三条不是实拍模型成绩。

字段缺失时默认轮次unversioned、模型unknown、类型unknown、流程unknown。未标注来源单独显示为“来源未标注”；其他自定义来源显示其名称，只有明确标为photo的记录进入实拍组。这些字段必须是字符串。旧版把来源缺失默认成photo的行为已修复；老记录仍可读取，但缺失信息不是实拍证据。

页面pipelineId是配置JSON哈希的前12位；最新Node批量报告pipelineId是引擎代码+配置的完整哈希。新配置均包含pipelineVersion，避免本轮共享修复沿用旧参数指纹。两者不是同一标识算法，不能仅凭它们不同推断处理参数不同；流程版本仍需随依赖修改维护，完整代码归档不可由配置哈希替代。

### 6.4 导出、恢复与导入限制

页面把记录存入当前来源的localStorage，键名 `ocr-photo-evaluation-v1`。`readRecords`解析并校验；内容损坏会报错，不静默清空。`saveRecords`验证后保存；`annotateRecord`返回新数组，`summarizeExperiments`不修改原始预测。

“导出全部记录”生成包含 `schemaVersion:1`、`exportedAt`、`records` 的JSON文件。导入接受**记录数组**或顶层有`records`数组的对象，文件上限10 MiB、合并后最多2000条，每条数字串最长1000字符。

当前 `development-report.json` / `test-report.json` 的记录在 `summary.records`，**不能把完整批量报告直接当作页面导出文件导入**。需要在副本中取出 `summary.records`，作为顶层记录数组保存，再导入；早期开发报告缺失的来源/轮次字段须如实补充并注明“由旧报告整理”，不要伪造原始时间或版本。标准单字训练报告也不是页面记录文件。

导入按id合并：同id且对象JSON序列化完全相同则不重复；同id但内容不同会拒绝，保留本机原记录。当前判等对字段顺序也敏感，格式整理后遇到冲突应检查内容，而不是随意换id绕过。

导入时先验证输入记录，合并后再次调用 `validateRecords`；因此**同id内容冲突、不同id但imageId+experimentId相同的同图同轮重复，都会被拒绝**。不能通过修改id把一次重试伪装成新增测试样本。若记录没有imageId或experimentId，或同源图片经压缩/转码后有不同文件哈希，这层检查仍不能证明来源独立；需要接收台账追踪原图、书写者及派生关系。跨轮保留同一原图是合法对照，但不增加独立原图数。

## 7. 错误分析与优化：一次只验证一个假设

### 7.1 从最早异常的阶段开始

| 观察到的现象 | 可能原因 | 需要的证据/下一步 |
|---|---|---|
| 原图横竖不对或缺字 | 方向元数据、保存方式、拍摄不全 | 原文件与解码图；先决定是否符合范围 |
| 二值图吞掉纸面或笔画 | 光照、阈值、去噪 | 原图/灰度/二值对照；开发集尝试另一阈值 |
| 框数量与字数不同 | 断笔、粘连、小域过滤 | 框与笔画位置；不利用真值长度强行分割 |
| 框数对但字形被压扁/截断 | 包围框、灰度掩膜、归一化 | 28×28字符图、边缘与质心 |
| 字形完整而标签错 | 模型对字迹覆盖不足 | 候选分数、单字混淆、开发来源分布 |
| 看似正确但评估有误 | 前导零丢失、答案错标、评分方向 | 原图、原始预测、答案和编辑对齐 |

替换并不一定等于“CNN错”，删除也不一定等于“分割少框”；错位对齐可产生多种等价解释。文本指标告诉我们发生了什么编辑，图像证据才能帮助解释为什么。

### 7.2 对照实验怎样保持公平

固定同一组开发来源、模型、样本纳入规则和正确答案，只改变一个配置，例如Otsu→局部均值；两轮都保留所有有效图片的首次结果。记录CER、整串正确率、空结果数、框数异常及耗时，不只展示改善的那张。

一个纯手算开发对照：真值两张分别`12`与`1203`；配置A预测`12`、`123`，CER1/6、整串1/2；配置B预测`12`、`1203`，CER0/6、整串2/2。这说明在该两图集合上的改善，不代表新照片也100%。如果为了修复B又把A弄错，必须在同一集合重新汇总。

不同长度、字迹、轻微倾斜和阴影可分别分层看结果；当前HTML没有自动按这些条件分层的控件，应以照片台账和导出记录辅助分析。样本很少时优先列逐图错误和分子/分母，不宣称稳定总体水平。12条全对仍只说明这12条全对。

### 7.3 失败之后怎样进入下一轮

先保存当前模型与原始评估，把失败照片加入下一轮开发；之后新增其他来源/书写者的照片做未见验证。已被查看、调参或用于训练的照片，不能继续称为新模型的独立未见测试。

第24章拒识阈值可以用于研究“高分接受、低分交人”的策略，但第25章当前未接入该拒识器。如实验将合法照片拒识为空，应继续计删除和整串失败；可以另报人工复核覆盖率与被接受样本准确率，不能用后者代替完整端到端成绩。

这两条完整演示从t10k准备测试行到执行真实推理。仓库已保存一次冻结运行的 `test-manifest.json`、`test-freeze.json` 与 `test-report.json`，日常学习先读它们即可；**不要为挑配置反复运行这组测试**。

需在另一环境复现时，先保存现有清单、freeze、report及图片副本。当前脚本按mode写固定文件名，会覆盖同名产物，也没有“一次测试后永久锁定”的防重跑机制；`experimentId`固定为`test-frozen-v1`，不是每次自动生成新轮次。因此复现应在副本工作目录中进行，并在归档说明中注明是复现，不是新独立测试。

流程指纹在逐图推理前写入；清单里的真值用于挑选合成源数字和最终评分，但从未作为 `recognizePhoto` 的输入。后者只接图、归一化函数、模型回调与冻结参数。

### 8.4 接入真实照片清单

浏览器逐图导入是现场主入口，便于观察。需批量复现时，按现有manifest结构另建照片清单：顶层包含 `schemaVersion`、独立 `mode`、`description`、`rows`；每行提供唯一id、相对清单所在目录的path、字符串truth、imageId、`sampleKind:'photo'`，以及必要的exclusionReason和外部来源台账。

例如清单放在 `26-validation/photos-rehearsal-manifest.json`，其中路径 `photos/p01.jpg` 指向同目录下photos文件夹；运行：

```bash
node 26-validation/evaluate-images.js 26-validation/photos-rehearsal-manifest.json
```

这是一份**需要真实图片与标注后自行建立的清单示例名称**，当前未提供这些照片。mode应区分预演与现场，且不要含路径分隔符；脚本将据此在第26章目录生成报告和冻结文件。当前脚本使用内置Otsu配置，不提供命令行阈值选项，不能凭文档自行添加不存在的参数。

批量入口先通过 `manifest.js` 校验，再加载模型和写冻结记录：id须唯一，图片路径须非空，同一个规范化路径或同轮同imageId不能重复计数，答案须遵守字符串约定。mode限1–80位字母、数字、连字符或下划线，首位为字母或数字。缺sampleKind的行保留为unknown，不增加realPhotoCount。此检查能发现相同路径、显式来源标识的重复；重编码图片、不同路径下未标同源的副本仍需结合原图台账检查，不能据此保证书写者独立。

### 8.5 复现应核对哪些对象

| 对象 | 核对内容 | 不一致时如何解释 |
|---|---|---|
| 模型文件 | modelId、weightsSha256、输入版本 | 已换模型，不能直接复述旧分数 |
| 源数据/划分 | 原文件校验、sourcePart/index、split | 已换输入或出现同源问题 |
| 清单/图片 | truth、图像哈希、变换参数、范围判定 | 样本或标签变化，需新记录 |
| 流程 | config、引擎指纹、共享依赖与锁文件 | 需归档具体变化；配置相同未必代码相同 |
| 环境 | Node/TFJS/Sharp、CPU/WebGL、浏览器 | 浮点/缩放/耗时可能不同 |
| 输出 | 原始prediction、S/D/I、分子/分母 | 先核查逐图差异，再解释汇总差异 |

模型报告中的151.357秒是当时训练整体流程测量，推理报告的elapsedMs是第25章核心识别耗时；不能用这些数字承诺其他机器训练/识别速度。照片解码与页面渲染也不在核心elapsedMs内。

## 9. API、HTML操作与八个Node实验

### 9.1 API与字段对应

评分算法来自 `shared/24-post-processing`，记录管理来自 `shared/26-validation`，浏览器与Node复用同一实现。

| API | 输入→输出 | 关键行为 |
|---|---|---|
| `alignSequences(truth,prediction)` | 两串→distance、S/D/I计数、alignment | 真值到预测；支持空串；按码点对齐 |
| `evaluatePredictions(records)` | 记录数组→汇总与逐条评分 | 不推理、不纠错、不修改输入；含有效失败 |
| `validateRecords(records)` | 记录数组→原数组或抛错 | 最多2000条、id唯一非空字符串、串长≤1000；imageId与experimentId均非空时同图同轮唯一；再调用评分验证 |
| `readRecords(storage)` | 提供getItem的存储→数组 | 不存在返回[]；损坏内容报错 |
| `saveRecords(storage,records)` | 存储、数组→写入JSON | 先验证；不隐去失败 |
| `appendRecord(records,record)` | 旧数组、新记录→新数组 | 同图同轮拒绝；不覆写首次预测 |
| `annotateRecord(records,id,truth,reason)` | 数组与标注→新数组 | 修改答案/排除理由/标注时间，保留prediction |
| `summarizeExperiments(records)` | 数组→实验组数组 | 四字段分组，每组调用evaluatePredictions |

`alignSequences`的alignment每项含 `operation`、`truth`、`prediction`、`truthIndex`、`predictionIndex`；缺口是null，界面显示∅。`evaluatePredictions`结果字段：

| 字段 | 含义 | Node实验2值 |
|---|---|---:|
| `totalSamples` | 输入记录总数 | 2 |
| `evaluatedSamples` | 有标签且未排除的记录数 | 2 |
| `pendingSamples` / `excludedSamples` | 待标注/排除数 | 0 / 0 |
| `failedSamples` | 有效记录中的空/失败状态数 | 0 |
| `totalTruthCharacters` | 有效真值字符总数 | 6 |
| `substitutions` / `deletions` / `insertions` | S/D/I合计 | 0 / 1 / 0 |
| `totalErrors` | S+D+I | 1 |
| `microCER` | 总编辑数/总真值字符数 | 1/6 |
| `exactMatches` / `exactMatchAccuracy` | 全对记录数/比例 | 1 / 0.5 |
| `records` | 原字段加disposition、included、failed、distance、cer、exactMatch、alignment等 | 2条可逐项核对记录 |

公共第24章评分函数允许未指定id而自动补名，第26章持久化入口要求唯一字符串id；不要把宽松的数学函数输入约定误当成可直接导入的记录格式。

### 9.2 HTML建议操作

1. 从第25章保存一条prediction已有、truth为空的记录；进入或刷新第26章，看到待标注数量，指标不把它计入。
2. 依据原图补上正确答案，点击该行“保存标注”；观察分子/分母变化，原预测不变。
3. 点“查看对齐”，读上方真值、下方预测及M/S/D/I；把∅解释成对齐空位，而非真实数字0。
4. 用一条预先标明的课堂例子观察空预测的3次删除，再检查真实记录的排除理由；不要为演示好看排除有效失败。
5. 切换实验组，确认不同轮次、模型、来源、配置没有被混成一项指标。
6. 导出全部记录，在另一份浏览器环境导入并复核数量；同时保管原图片。已有同id不同标注时会冲突，应保留两份导出对照后处理。

HTML百分比保留1位小数，例如1/64显示1.6%、11/12显示91.7%；原始JSON保留比例0.015625、0.916666…，不是指标换了口径。页面读取localStorage发生在加载时，另一个已打开页面保存后需刷新评估页。

### 9.3 Node八个实验的默认输出

| 实验 | 输入/操作 | 应核对的结果 |
|---|---|---|
| 1 漏字对齐 | `1203→123` | M/M/D/M，距离1，CER25% |
| 2 micro聚合 | `12→12`、`1203→123` | 总真值6、D1、CER1/6、整串1/2 |
| 3 字符串边界 | `00110→00110`、`00110→0110`、`1→1111` | CER依次0、0.2、3 |
| 4 三类状态 | 有效空预测、待标注、多行排除 | 有效1、真值3、D3、CER1、待标注1、排除1、失败1 |
| 5 首次与补标注 | prediction0010，补truth00110，再同轮追加 | prediction不变，原数组不变，同图同轮被拒 |
| 6 分组与存储 | 模型/来源不同的3条记录 | 3组，各CER0.2；内存模拟存储往返一致 |
| 7 读取真实报告 | 已保存训练与开发报告 | 标准9769/10000；开发12行64位、S1、CER1/64、整串11/12 |
| 8 现场流程 | 打印采集→识别→标注→导出路线 | 强调同源分区和实拍待测，没有生成现场成绩 |

截至本次审读，实验7读取的是标准单字与开发报告；冻结测试结果见test-report及§2.3，不能假称默认入口已经重新推理了全部测试行。入口通过的是有具体数值的评分/记录断言和报告读取，不是照片准确率验收。

## 10. 排障与常见误区

| 现象/误区 | 原因或检查点 | 正确处理 |
|---|---|---|
| 页面没有记录 | 未从第25章保存；地址/端口/浏览器不同 | 同一来源打开并刷新；导出文件可跨来源恢复 |
| CER显示“—” | 无有效非空真值 | 检查待标注/排除数；不是0错误 |
| 300%看似异常 | 预测多字超过真值长度 | 查看S/D/I；保留3/1，不截断 |
| 录入00110后变成110 | 外部表格或导入程序转数值 | 答案字段保持文本；数字类型会被验证拒绝 |
| 同一图保存被拒绝 | 同imageId、同experimentId | 保留首次；开发重试换轮次 |
| 保存结果与页面当前预测不同 | first与latest不同 | 查看首次记录，下一轮再保存新配置 |
| 导入完整test-report失败 | 数据在summary.records | 从报告副本取记录数组，保留原始报告 |
| 导入时id冲突 | 本机已有同id但内容不同 | 比较两份记录，保留原始预测与标注来历，不盲目换id |
| 换id后导入仍被拒绝 | imageId和experimentId仍与已有记录相同 | 同图同轮也受保护；保留首次，开发重试使用新轮次 |
| 浏览器存储读失败 | JSON损坏、容量或浏览器限制 | 保存已有原始数据再排查；不要先清空所有记录 |
| 记录显示“来源未标注” | 缺sampleKind，默认unknown | 按来源清单补元信息并保留修订依据；不能直接当实拍 |
| failedSamples为0但有错字 | failed是空/失败状态，非一般错串 | 看exactMatches和逐图alignment |
| 全对就宣称实拍100% | 混淆标准/合成/实拍及样本量 | 同列来源、数量、分子分母，实拍0不报百分比 |
| 换了方法只留最好结果 | 看测试结果后选择配置 | 旧轮保留，开发对照另存，再采新未见照片 |
| Node评估结束但退出码非0 | 有图片读取/推理异常，或全局错误 | 检查report中error与有效样本数量；不要仅看最后CER |
