## 2. 整理自己的讲稿时，怎样使用三件套

| 入口 | 用它完成什么 | 为讲稿留下什么 |
|---|---|---|
| README | 逐点读动机、直觉、公式、符号/维度、算例、参数、局限 | 自己的一句话解释、关键公式、一个易错点 |
| HTML | 改一个输入或参数，观察中间状态和结果 | 可重复的操作顺序、对照截图与对应条件 |
| Node index.js | 从自带小输入看计算与断言，区分受控/真实模型实验 | 输入、中间数值、输出和解释，不只截最后一行 |
| 共享实现 | 核实讲义约定与实际行为 | 需要讲源码时只挑关键计算，不逐行翻完整模块 |
| 训练/评估报告 | 核实数据来源、版本、分子分母 | 真实证据及其可支持范围 |

可为每个技术点自填“为什么需要、输入输出维度、手算一步、改哪个参数、哪里会失败、怎样验证”六项。README中的“知识点→文档→HTML→Node实验”表可直接作为备课索引，不代替你自己的归纳。

第25章适合重点挑选：alpha的255/127、Otsu的`t=0`与`<=t`、积分图角点均值25与阈值17、断笔为何仍是3框、8×13裁剪到784维、模型得分与准确率。第26章适合挑选：`1203→123`的一次删除、两图合并的1/6与1/2、空预测全部计删除、同图同轮首次结果保护。

首次分享若只讲14–15章，开头可加载一次**明确标为合成开发样例**的`001208`说明最终目标，随后回到原理。无需为了第一节就临时跳过中间章节或现场重新训练。

### 3.1 日常学习与现场推理的最短准备

项目在Node 24环境运行过。首次安装、构建并启动：

```bash
cd /Users/wuxiuran/project/ocr-learn-ai
npm ci
npm run build
npm start
```

已安装依赖时无需重复 `npm ci`。保留服务窗口，浏览器统一使用：

- [课程首页](http://127.0.0.1:4173/)

普通推理服务只绑定127.0.0.1，图片通过浏览器文件选择器在本机处理。现场不会自动从群聊收图或向群里发结果；同事发图后由你手动保存并导入。

### 3.3 只有模型/数据缺失，或要复现训练时才走长训练

已准备好的模型可直接用于课程和现场，不要求每次训练。若需要重现真实训练，先按[第17章讲义](../17-cnn-classifier/README.md)操作，并指定新的输出目录保留现有模型。

浏览器WebGL训练需要正常课程服务运行在 `http://127.0.0.1:4173`，另一个终端启动本机数据/模型桥：

```bash

```

首次会下载并核验MNIST原始数据；打开[第17章训练页](http://127.0.0.1:4173/17-cnn-classifier/train.html)，点“开始真实训练”。桥使用4174端口，并按当前实现允许4173课程来源；不要在这一训练流程中随意更换端口。输出目录若已有模型会拒绝覆盖，应使用新的目录名。

也有CPU训练入口，使用独立目录：

```bash
node 17-cnn-classifier/train.js --output 17-cnn-classifier/model-cpu-reproduction-0922
```

这是完整训练，默认55,000/5,000、5轮，纯JavaScript CPU可能明显更慢。现有报告记录WebGL训练约141.18秒、含保存和CPU评估约151.36秒，只是当时机器的测量，不承诺复现耗时或权重逐位相同。训练应在分享前完成，现场以加载和推理为主。

## 4. 准确介绍目前测量到了什么

每次引用数字同时说明来源、样本量、指标和模型版本，不使用笼统的“OCR准确率”。

| 证据 | 当前结果 | 讲解时必须带上的范围 |
|---|---|---|
| 标准单数字 | 9769/10000=97.69% | MNIST已裁剪单字，非照片整串 |
| 合成开发行 | 12行64位，S1/D0/I0，CER1/64=1.5625%，整串11/12≈91.67% | 字迹来自模型验证分区，排版程序合成；保留`987654→987659`失败 |
| 冻结合成测试行 | 12行64位，S/D/I全0，CER0/64，整串12/12 | t10k源字迹，小规模合成工程回归；不能当实拍保证 |
| 多书写者手机照片 | **0张；CER和整串正确率待测** | 需要同事真实照片与独立答案，预演/现场分别记录 |

测试分高于开发分不矛盾：它们是不同字迹、很小的样本集合。展示[开发报告](../26-validation/development-report.json)的失败，再展示[冻结测试报告](../26-validation/test-report.json)，不要隐去不成功的开发结果。

[测试冻结记录](../26-validation/test-freeze.json)在推理前保存模型、配置和代码指纹，[测试清单](../26-validation/test-manifest.json)保存源索引、变换与图片哈希。已冻结测试的复现命令为：

```bash
node 26-validation/prepare-fixtures.js --test
node 26-validation/evaluate-images.js 26-validation/test-manifest.json
```

这组已经执行过，备课通常读取现有报告即可。需要复现时保留原始产物，在副本工作目录运行；脚本会覆盖同mode的manifest/图片、freeze和report，不会自动锁定首次运行。不要把这组已看过的测试行再用来挑阈值，也不要把复现轮次当新增独立测试数据。

## 5. 预演：复现真实的收图、保存、导入链路

### 5.1 预演要解决的问题

模型准备与合成样例只能确认技术流程能运行。预演还要验证实际使用的群聊、保存方法、浏览器、投影屏、照片格式与采集条件。请在9月22日前留出独立预演时间；下面是待执行流程，当前不宣称已经完成多书写者实拍预演。

建议邀请多位同事，各写若干不同长度的数字串，覆盖前导零、连续重复、不同字迹、轻微倾斜与光照变化。数量按可用时间决定，报告始终写实际数量；不预先规定一个“达到就算高准确率”的门槛。

输入说明保持简单：白纸、深色笔、单行从左到右，只写0–9；数字之间留基本间隔，整串完整入镜。内容尽量使用随意编写的练习数字，便于共享演示。明显多行、重叠、严重透视和复杂背景属于本版未承诺处理的范围。

### 5.2 先划分来源，再进行调整

早期用来改参数的照片记为开发。调好后冻结模型和配置，再从未用于调参的原图/书写者收集预演验证照片。若把预演失败用于改进，下一版验证须使用新照片；现场新收图另建现场轮次。

有writerId时按书写者分区，没有时至少按原图分区并说明限制。同一照片的原图、群聊压缩图、旋转图及字符裁剪都属于同一来源；字节哈希变了也不证明它们独立。

### 5.3 预演操作与应保存的证据

| 步骤 | 操作 | 应能核对的证据 |
|---|---|---|
| 1 准备 | 启动课程服务，加载模型与开发样例 | 页面modelId，样例来源标记，三张中间状态 |
| 2 冻结 | 写下本轮模型、阈值、自动/手动角、去噪状态 | 预演配置说明与实验轮次名 |
| 3 收图 | 同事真实写字拍照发群，你按现场方式保存 | 原文件、书写者/原图来源台账 |
| 4 识别 | 每图首次运行，先保存结果，不因错误换图 | 第25章完整原始预测及失败记录 |
| 5 标注 | 独立核对纸面/书写者答案，再补真值 | 正确答案与预测分开，保留前导零 |
| 6 排障 | 查看二值图、字符框和28×28卡片 | 一例成功、一例失败的输入/中间结果截图 |
| 7 汇总 | 检查有效、待标注、排除及接收总数 | 逐图记录、S/D/I、CER分数与整串分数 |
| 8 归档恢复 | 导出JSON并在另一环境导入核对 | 文件可读，来源与轮次不混，记录数量一致 |

读取失败的文件不会自动成为第25章可保存记录，另记接收台账及原因。有效带字照片识别为空则必须保存失败并补真实答案，例如`305→空`是3次删除，不得因为没有输出就丢掉。

## 6. 现场照片的具体操作

### 6.1 从群里保存照片

1. 同事写完后完整拍下数字串并发群，你打开图片保存到本机的本次活动文件夹。尽量保存实际图片文件；若使用群聊压缩版，就把该版本作为本轮实际输入保留。
2. 为每张图记录简短来源编号、原文件名、书写者标识（可用匿名编号）、收到时间、是否为同一原图派生物。不要把“第一张失败后的重拍图”当成没有关系的新来源。
3. 按JPG、PNG、WebP准备；第25章支持文件≤20 MiB、最长边自动缩到1200。HEIC等未支持格式需事先转成支持格式，保留原件和转码关系。原图横竖不对时先转正，记录派生关系。
4. 正确答案从实际纸面或书写者确认获得。不要从模型预测反推答案，也不要在不知道内容时把预测直接复制为真值。

### 6.2 导入与首次识别

1. 打开[第25章](http://127.0.0.1:4173/25-ocr-engine/)，确认“模型已就绪”及本轮模型标识。
2. 将实验轮次设成清楚的名称，例如`现场-2026-09-22-轮1`；这是命名示例。确认阈值、去噪与角度符合本轮冻结配置。
3. 点击“选择照片”，选刚保存的文件。等“照片已导入”，核查原图、朝向及完整性；每次导入会清空上一张的答案与当前结果。
4. 点击“开始识别”，观察完整字符串、框数量、实际校正角，以及阈值图和字符卡片。先把本轮首次结果保存；可以暂留答案为空，之后在第26章补。
5. 对有效照片的空串或报错，同样保存首次结果。若是文件根本读不进来，在接收台账记原因；页面不会自动替你记这类文件。

不要用真值长度辅助分框。每个框的数字得分可以解释“模型偏向哪一类”，不能对听众称为识别准确率；即使显示100.0%也可能只是舍入后的高得分。

### 6.3 输入正确答案、核对与保存

在“正确数字串”输入实际答案，例如`00110`，保留前导零与连续11，只用0–9。点“核对”查看当前结果的CER与整串判断。若之前尚未保存，点“保存本轮首次结果”；已保存的待标注记录应去第26章补答案，不要再次保存成新样本。

**“核对”针对最新预测，“保存”针对本轮首次预测。** 如果第一次是`0010`，调整参数后当前画面变`00110`，同轮保存的仍是首次`0010`。需要演示调参，先确保首次结果已保存，换一个明确的开发轮次，再重新识别并保存对照。调参后成绩不混入原现场冻结轮次。

保存按钮与导入记录都有重复保护：同id内容冲突会拒绝；不同id但具有同一个imageId与experimentId的同图同轮重复也会拒绝。完全相同的已存id在跨文件合并时不重复计数。不要通过改id伪装新样本；无imageId/experimentId、不同文件哈希或不同轮次也不能证明来源独立，仍以原图台账为准。

### 6.4 查看批次结果并导出

1. 进入[第26章](http://127.0.0.1:4173/26-validation/)，若原先已开着，刷新后读取刚保存的记录。
2. 选择本次现场实验组，核对模型、样本类型、处理配置；合成样例、预演照片、现场照片分开。
3. 为待标注行填写答案，点该行“保存标注”；原始预测不会改变。只有依据事先输入范围的排除才填写明确原因，合法识别失败仍纳入。
4. 点“查看对齐”，上排是真值、下排是预测；M匹配、S替换、D漏字、I多字，∅为空位。
5. 同时展示CER的编辑次数/真值字符数、整串正确数/有效照片数、待标注、排除和失败数；与接收台账核对没有漏图。
6. 点“导出全部记录”，保存当天下载的 `ocr-evaluation-日期.json`。它导出所有组，不只是当前选中组；可在操作系统中加轮次说明改名，避免同日多次下载混淆。

例如两图`12→12`与`1203→123`，整体CER是1/6≈16.67%，整串正确率1/2=50%；不是把0%和25%平均为12.5%。若没有有效已标注样本，比例显示“—”，不能报告为0错误。

## 7. 记录保存与恢复

### 7.1 一次活动建议保留的文件

| 资料 | 为什么要保留 |
|---|---|
| 原始照片与实际导入版本 | JSON不包含图片；可重新检查方向、压缩和笔画 |
| 接收/来源台账 | 找回书写者、原图、派生关系、读取失败与排除理由 |
| 正确答案及确认依据 | 复核错标，保持答案独立于模型输出 |
| 浏览器导出的记录JSON | 恢复首次预测、轮次、模型、配置、状态和评分 |
| 成功/失败中间结果截图 | 浏览器记录不包含完整的阈值图和28×28候选画面 |
| 模型目录、配置与课程版本 | 恢复具体输入处理及权重，不混用新模型旧成绩 |
| 已发布的汇总副本 | 保留原轮事实，之后开发结果另存 |

照片文件名改变不影响图像哈希，但来源台账要更新路径。模型和记录在本机可运行，不代表localStorage是长期备份；关闭浏览器通常仍保留数据，清理站点数据或更换来源则可能读不到。

### 7.2 在另一浏览器或机器恢复

准备同一课程与模型文件，启动HTTP服务，打开第26章，选择“导入记录JSON”。页面接受记录数组，或顶层含records数组的对象；大小≤10 MiB，合并后≤2000条，每串≤1000字符。使用同一个浏览器来源时第25/26章共享localStorage；`localhost`和`127.0.0.1`、不同端口、不同浏览器都是不同存储环境。

批量图片报告的记录位于 `summary.records`，完整 `test-report.json` / `development-report.json`不是页面直接导入格式；要展示其中逐图对齐，先从报告副本取记录数组另存，保留原报告及转换说明。早期开发报告缺少部分后加版本字段，不要补造历史冻结信息。标准MNIST单字报告也不能直接导入成实拍记录。

遇到冲突时先保留本机导出和外来文件：同id但内容不同拒绝覆盖；不同id却同imageId+experimentId也拒绝。查明是重复运行、标签修改还是来源信息缺失，再决定如何整理档案。不能为了导入成功改掉失败预测、虚造来源或删除有用的历史记录。

## 8. 现场故障的处理顺序

| 状态 | 当场处理 | 对结果怎么交代 |
|---|---|---|
| 模型未加载 | 检查服务、bundle、model.json与weights.bin；恢复后重新加载 | 模型未就绪时没有可展示的真实预测 |
| 合成样例缺失 | 分享前运行prepare-fixtures并确认数据/split | 夹具准备问题，不是实拍模型成绩 |
| 文件不支持/损坏/太大 | 另存支持格式或适度缩小，保留原件及派生关系 | 接收台账单记原因，当前页面不会自动记这条 |
| 有效照片预测空串 | 保存首次失败、补正确答案，展示二值图和框 | 空预测按真值全部删除计入 |
| 一框有两字/一字多框 | 展示分割边界，在新开发轮次比较方法 | 保留冻结轮次错误，不靠答案修框 |
| 方向错误 | 检查解码方向；必要时在照片工具转正 | ±15°小角校正不能承担90°方向修复 |
| 保存与画面不一致 | 解释first/latest区别，去评估页查看首次记录 | 调参前后的结果分轮呈现 |
| 导入拒绝重复 | 核对id及imageId+experimentId | 同图同轮不会因换id成为新样本 |
| 临时没有真实照片可用 | 用合成开发样例解释算法与当前报告 | 明说实拍未测，不将合成结果重新命名 |

如果一个问题短时间内不能排除，现场仍可讲已保存的真实报告与受控Node算例，但必须说明当前运行中断发生在哪一步。不要把截图或手算示例当作刚刚完成的实时识别。

## 9. 预演后与每次分享后的复盘

每轮先冻结并归档原始结果，再选一两个代表性失败追查：是原图不合范围、阈值丢笔、框错误、归一化失真，还是分类器混淆？像开发报告中的`987654→987659`，只能先确定有一次替换；6个框不自动证明裁剪和归一化都正确。

在开发集合中一次改变一个参数，比较同一批输入的完整结果。用过的预演/现场失败照片可以成为下一版开发数据，但它们已不再是下一版未见测试。新版本需要新的独立来源，跨版本对照和新增样本数分开写。

可自行填写的复盘栏目是：活动日期与轮次、模型/流程版本、采集范围、来源数量、有效/待标注/排除/失败数、S/D/I及真值字符数、CER、整串正确数/分母、代表性错误、下一轮假设。没有数据的栏目填写“待采集/待标注”，不要以0%代替未测量。
