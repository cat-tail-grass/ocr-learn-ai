# 25. OCR 引擎整合：从照片到完整数字串

本章把前面的算法接成一条可以检查、重复运行的识别流程。输入是**白纸、深色笔、单行横写、有基本间隔、完整入镜的手写数字串**；输出是保留前导零和重复数字的字符串，以及解释这次预测所需的中间图像、字符框和模型得分。

三个主要学习入口是本讲义、[HTML 交互实验](index.html)和 [Node.js 教学实验](index.js)。`browser.js`、`shared/25-ocr-engine`、第17章模型和第26章图片夹具是辅助文件。阅读时按“理解一个问题 → 手算 → 操作 HTML → 核对 Node 输出”推进。

## 1. 为什么需要 pipeline：让每一步有可检查的契约

### 1.1 问题、流程与维度

模型只会回答“这个 28×28 的区域像哪个数字”。它不会自动保证图片方向正确、一个框只有一个数字，也不知道漏掉了哪一位。引擎的工作是把照片变成符合模型契约的区域，并保留转换证据。

```text
文件 Blob / 本地图片
  ↓ 方向处理、白底合成、最长边缩放
RGBA：W×H×4
  ↓ flattenImage；可选 medianFilter(3)
灰度图 gray：W×H×4，R=G=B
  ↓ Otsu / fixed / adaptive；可选校正后重新二值化
二值图：白背景255、深色前景0
  ↓ 小连通域过滤 + 列投影分组
K 个字符框，按 x 从小到大排列
  ↓ 用过滤后掩膜清理灰度，逐框裁剪，prepareDigit
K 份 Float32Array(784)，各自视作 [1,28,28,1]
  ↓ 已加载 CNN
每框10个得分 → argmax标签 → 按顺序拼接
完整字符串 + 中间图像 + 字符框 + 得分 + 状态 + 总耗时
```

`W,H` 是处理图的宽高，单位是像素；`K` 是**算法找到的区域数**，由照片决定。真值长度不传给引擎，不能为了答案有6位就强行切成6框。

若一张 4000×3000 的照片缩到最长边1200，则缩放系数为 `s=min(1,1200/4000)=0.3`，处理图为1200×900，RGBA数组长度为 `1200×900×4=4,320,000`。若分出6框，模型调用6次，每次输入784个数，输出10个数；它不是一次把整张照片当作一个数字。

### 1.2 三层职责及状态

| 层次 | 对应实现 | 职责与不确定性 |
|---|---|---|
| 文件/界面层 | `browser.js`、第26章图片评估脚本 | 解码文件、加载模型、调用共享算法、显示与保存 |
| 图像引擎层 | `shared/25-ocr-engine/index.js` | 预处理、分割、裁剪、顺序拼接；不依赖 DOM 或答案 |
| 模型层 | 第17章 `prepareDigit`、模型文件、预测回调 | 输入标准化和学习到的0–9分类 |

`recognizePhoto` 通过参数注入 `prepareDigit` 和 `predict`。这种拆法能在受控实验中先验证“5个框是否按顺序拼成 `00110`”，再单独用真实模型检验分类。受控回调只证明接口与字符串拼接，不构成模型成绩。

共享返回值中，找到字符为 `status: 'recognized'`，无字符为 `status: 'empty'`；非法参数、归一化空区域或非法模型输出会抛错。浏览器保存时把空结果和异常记成 `status: 'failed'`、`prediction: ''`。**运行成功不等于识别正确**：返回了字符串仍须与答案比较。

当前 `elapsedMs` 是共享识别入口内的总耗时，包含预处理、逐框归一化和预测；不含文件解码、模型下载及界面绘制。它不是每阶段耗时表。假设一次输入处理耗10 ms、分割8 ms、6个字符各推理2 ms，核心总耗时约30 ms；这只是拆解算例，机器上的实测值以输出为准。

## 2. RGBA 与 alpha：看不见的黑色不应成为笔画

### 2.1 为什么不能直接读取 R 通道

透明 PNG 的透明区域可能存成 `[0,0,0,0]`。仅看RGB会把它当黑色，实际叠在白纸上却应该是白色。`flattenImage` 先合成白背景，再调用第03章加权灰度。

对像素 `(x,y)`，数组起点为：

```text
i = 4(yW+x)
alpha a = A/255
Cwhite = a·Csource + (1-a)·255，C ∈ {R,G,B}
g = round(0.299Rwhite + 0.587Gwhite + 0.114Bwhite)
```

`R,G,B,A,g` 的范围均为0–255；`a` 无量纲，范围0–1。三个通道合成写入 `Uint8ClampedArray` 后会量化，随后灰度函数再次取整。这里沿用课程的像素灰度约定，没有额外实现线性光空间的物理亮度计算。

具体算例：

| RGBA输入 | 白底合成 | 灰度结果及含义 |
|---|---|---|
| `[0,0,0,0]` | `0×0+255×1=255` | 255，透明背景不算笔画 |
| `[0,0,0,128]` | `255−128=127` | 127，半透明黑色成为灰色 |
| `[0,0,0,255]` | 0 | 0，完全不透明黑笔画 |
| `[255,0,0,255]` | 不变 | `round(76.245)=76` |

例如 `W=5,x=2,y=1`，`i=28`，该像素占数组第28–31项，不能用 `yW+x` 直接索引RGBA字节。

### 2.2 浏览器和 Node 的接入边界

浏览器先在白底Canvas上绘制已解码图片，再交给共享引擎；即使共享模块被Node直接调用，也仍有 `flattenImage` 兜底。输入尺寸由 `validateImage` 检查：正整数宽高、恰好 `4WH` 个通道值、总像素数不超过2,000,000。

页面接受 JPG、PNG、WebP，文件上限20 MiB（页面简写20 MB），最长边最多1200像素，不放大小图。共享函数的200万像素限制与文件字节上限是两件事：压缩后很小的JPEG，解码后也可能很大。

透明背景、纯白空图、纯黑图分别用于验证三种边界：透明背景应变白；白图应没有框；黑图应触发前景面积过大提示。alpha处理不能消除纸张上的阴影，后者要交给阈值方法。

## 3. 阈值：在照片里决定哪些像素属于笔画

### 3.1 固定阈值与 Otsu 的精确边界

固定阈值适合光照稳定、深浅分离明确的输入。本课程 `binarizeFixed(gray,T)` 采用：

```text
B(x,y)=0   当 g(x,y)<T
B(x,y)=255 当 g(x,y)≥T
```

所以 `T=128` 时，127是黑，128是白。照片接口允许 `T∈[0,256]`：0把全部像素变白，256把全部像素变黑；后者通常会被前景比例检查挡住。极端阈值适合解释边界，不是识别推荐值。

Otsu 根据256格灰度直方图自动找分界。设 `h[v]` 为灰度v的像素数、`N=WH`：

```text
C0=[0,t]，C1=[t+1,255]
n0=Σ(v≤t)h[v]，n1=N−n0
w0=n0/N，w1=n1/N
μ0=Σ(v≤t)v·h[v]/n0，μ1=Σ(v>t)v·h[v]/n1
σbetween²(t)=w0w1(μ0−μ1)²
t*=argmax σbetween²(t)
```

只比较两类都非空的候选。`w0,w1` 是比例，`μ0,μ1` 是灰度均值。本轮复核已将共享实现的 `variance` 统一为上式的概率加权类间方差；只重复整张图片的像素计数，不会改变这个方差。旧版返回的是 `n0n1(μ0−μ1)²`，比正确方差大 `N²` 倍；最优阈值虽相同，但数值与公式不一致。

**手算纯黑白输入 `[0,0,255,255]`：** `t=0` 时 `n0=n1=2`，两类均值0与255；类间方差为 `0.5×0.5×255²=16,256.25`，当前代码返回同一数值。`t=1…254` 产生相同分组；代码只在严格变好时更新，因此保留最早的 `t=0`。

此时前景必须是 `gray<=0`。若错误地调用固定阈值0，即测试 `gray<0`，所有黑笔画都会消失。当前 `binarizeOtsu` 实际调用固定阈值 `t+1`，将 `gray<=t` 转成整数灰度上的 `gray<t+1`，结果仍是 `[0,0,255,255]`。

Otsu最小化类内离散、最大化类间差异的思想来自[原论文](https://ieeexplore.ieee.org/document/4310076)。实现中的边界、概率权重和并列选择以本仓库第04章代码为准。算法计算量约为 `O(WH+256)`，但它不认识数字；一大片阴影也可能被划进暗类。

### 3.2 光照不均为什么需要局部阈值

同一张照片里，阴影下的白纸可能比亮处的灰笔画还暗，单个全局阈值难以同时处理。局部均值法比较像素与附近背景：

```text
T(x,y)=μwindow(x,y)−C
B(x,y)=0 当 g(x,y)<T(x,y)，否则为255
```

`C` 对应API的 `offset`，单位是灰度级；窗口边长 `blockSize=k` 为不小于3的奇数。默认 `k=41,C=8`，窗口在图像边缘截断，以**实际像素数**求均值，没有给缺失区域补零。

假设邻域均值180，`C=8`，局部阈值172：灰度160的像素保留为笔画，175成为背景。如果把C调大到25，阈值降为155，同一个160像素也会被清掉。因此**增大offset会减少黑色前景，可能去掉淡笔画**，不是“增强笔画”。

### 3.3 积分图如何把每次邻域求和变成四次读取

逐像素扫描 `k×k` 邻域需要约 `WHk²` 次累加。1200×900图、41×41窗口对应约18.15亿个邻域元素。`adaptiveMeanFast` 先建立一张 `(H+1)×(W+1)` 的 `Float64Array` 积分图P：

```text
P(y+1,x+1)=P(y,x+1)+Σ(u=0…x)g(y,u)
```

P顶部和左侧各留一条0边界。对于半开矩形 `[left,right)×[top,bottom)`：

```text
sum = P(bottom,right) − P(top,right)
    − P(bottom,left)  + P(top,left)
count=(right−left)(bottom−top)
mean=sum/count
```

数值例子及对应积分图：

```text
g（3×3）           P（4×4，含零边界）
10 20 30           0   0   0   0
40 50 60           0  10  30  60
70 80 90           0  50 120 210
                   0 120 270 450
```

右下2×2区域 `[1,3)×[1,3)` 的和为 `450−60−120+10=280`，均值70。左上像素使用3×3窗口时，窗口被截为2×2，和120、均值30；`C=8` 得阈值22，原值10变黑。中心像素的窗口覆盖全图，和450、均值50、阈值42，原值50变白。

对这张小图执行 `adaptiveMeanFast(g,3,8)`，输出为：

```text
  0   0   0
255 255 255
255 255 255
```

这同时说明局部阈值不会把任意亮度梯度“理解为白纸”；邻域过小，背景变化本身也会成为前景。积分图仅改变求和效率，不改变这个统计判断。构建和输出均为 `O(WH)`，额外内存为 `8(W+1)(H+1)` 字节；1200×900约8.66 MB，不含其他图像副本。

上面是独立的3×3手算图。**Node实验2的默认输入**是9×7图，灰度为 `(19x+31y) mod 256`，同样使用窗口3、偏移8。左上窗口为 `[0,19;31,50]`，和100、像素数4、均值25、阈值17，原像素0输出黑色0。脚本还将整张输出与第04章逐邻域求和实现逐字节比较；这验证的是算法等价，不能把一次运行耗时差当成稳定的性能倍数。

### 3.4 去噪和阈值怎么选

| 方法/选项 | 先观察什么 | 可比较的现象 | 主要代价与局限 |
|---|---|---|---|
| Otsu，默认 | 背景是否整体均匀 | 自动阈值后的笔画是否完整 | 阴影可能与笔画落在同一类 |
| 固定128 | 白纸与笔画是否有足够对比 | 同一输入与Otsu的差别 | 参数依赖拍摄亮度 |
| 局部均值41、8 | 全局方法是否吞入阴影 | 阴影附近的白纸能否变白 | 窗口太小丢结构；偏移太大丢淡笔画 |
| 3×3中值，默认关闭 | 是否有孤立椒盐点 | 小点减少，细线是否同时消失 | 细笔画/小间隙会改变；增加处理量 |

本引擎去噪在灰度图上、阈值之前执行。3×3邻域 `[255,255,255,255,0,255,255,255,255]` 的中值是255，能清除孤立黑点；但一条只有3个黑像素穿过该邻域的细线，其中值也为255。第05章的核大小权衡在这里会直接影响漏字率。

HTML开放方法选择、去噪和角度控制；窗口大小、offset、固定阈值数值通过共享API/Node实验研究，页面当前没有这些滑块。不要把正文参数表理解为页面已经提供了所有控件。

## 4. 连通域与列投影：把笔画分成字符

### 4.1 先去掉噪点，再决定字符边界

第09章的8连通域把上下左右及对角相邻的黑像素归为一组。但数字上下断笔时会变成多个域；两个数字相碰时又可能只有一个域。`segmentDigits` 因而分两步：**连通域用来过滤微小碎片，列投影用来决定字符框**。

连通域r的面积、包围框分别为：

```text
Ar = 区域内黑像素个数，单位px²
bbox(r) = (xmin,ymin,xmax−xmin+1,ymax−ymin+1)
Amin = max(3, round(0.007·Amax))    默认面积阈值
保留 Ar ≥ Amin 的区域
```

前景检测统一检查二值图的R通道 `<128`。若最初前景比例 `F/(WH)>0.55`，直接返回空框并提示前景面积过大。这个55%是输入防护启发式，不是从实拍验证得到的最佳阈值。

Node实验3用52×19图像画3个宽6、高11的矩形，左边界为5、20、35；第一块在 `y=9` 擦掉一行，并在 `(1,1)` 加一个黑噪点。它是受控几何图，不是真实数字。

连通域面积为30、30、66、66和1，最大面积66，所以 `Amin=max(3,round(0.462))=3`。噪点被清掉，上下两块30像素区域保留。初始前景有193像素、比例 `193/988≈19.53%`，不会触发55%保护。过滤后192个黑像素。

### 4.2 列投影与空白间隔

设清理后的二值前景 `F(x,y)=1[B(x,y)<128]`，行包围框高度为h：

```text
Pcol[x]=Σ(y在线框内)F(x,y)，长度W，单位是每列黑像素数
gap=max(1,round(0.025·h))    默认可合并的空白列数
当前非空列x与上一个非空列last之间的空白数=x−last−1
空白数>gap：开始新字符；否则接在当前字符后面
```

投影将垂直方向压成一维。同一个x位置即使上下笔画不连通，只要该列还有黑像素，就不会成为字符间隙。因此断开的第一块仍属于一个框。

上述Node输入过滤后的行框为 `(x=5,y=4,width=36,height=11)`。第一块占列5–10，中间块占20–25，最后一块占35–40；块间各有9列空白。`gap=max(1,round(11×0.025))=1`，9大于1，所以得到：

| 框序号 | x | y | width | height |
|---|---:|---:|---:|---:|
| 1 | 5 | 4 | 6 | 11 |
| 2 | 20 | 4 | 6 | 11 |
| 3 | 35 | 4 | 6 | 11 |

另一个一维手算例：投影 `[0,3,4,0,2,3,0,0,0,5,5,0]`，`gap=1` 时，列1–2与列4–5间只有一列空白，合成 `[1,6)`；列9–10形成 `[9,11)`。`gap=0` 会得到3段；`gap=3` 会把所有非空列合成1段。这说明gap是在“修补横向断笔”和“误并邻字”之间取舍。

代码中的区间右端是开边界 `last+1`，最终框坐标是清理后的整张处理图坐标。每段会再次计算局部上下边界，不把整行高度机械赋给每个数字；遍历方向自然保持从左到右顺序。

### 4.3 断笔、粘连和多行的失败边界

| 形态 | 可能结果 | 应检查的证据 |
|---|---|---|
| 上下断笔，但横向投影重叠 | 多个域仍归入一个字符框 | 灰度图可见断口，框数量不增加 |
| 横向断笔，空白列数超过gap | 一个数字被切成两个 | 单字位置出现两个窄框 |
| 两数字间距不超过gap | 两个数字被并框 | 框比正常单字明显宽 |
| 真实笔画面积小于minArea | 笔画或整个细小数字消失 | 阈值图有笔画，清理结果没有 |
| 两数字相互接触，无空白列 | 投影不能可靠分开 | 一个框覆盖两个数字，通常偏宽 |
| 多行数字 | 上下行可能投影重叠并混在一起 | 行框异常高；不存在多行阅读顺序恢复 |

框宽超过高度的1.25倍会产生“可能粘连”警告；笔画距图片边缘过近也会提示。警告只是待检查证据，不会自动补字、强制切开或拒识所有异常框。宽度正常也不能证明分割正确。

`minArea` 默认为相对最大连通域面积的阈值，极大污渍会抬高门槛，误删小字；`mergeGap` 依赖处理后的像素尺寸，不同缩放下不可直接比较同一个数值。先在开发集看框和笔画，再讨论调参。第06章的膨胀/闭运算能连接断笔，也能把相邻数字粘在一起，本版没有默认串联这些步骤。

## 5. 方向与倾斜：分别处理文件方向和文字行方向

### 5.1 照片方向不是一个小角度参数

手机JPEG可能靠EXIF元数据表示朝向。浏览器使用 `createImageBitmap(blob,{imageOrientation:'from-image'})`，按解码后的方向绘制；这对应 [HTML 标准的 ImageBitmap 方向约定](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html)。Node批量评估使用Sharp的无参数 `rotate()` 自动处理方向，然后白底合成与缩放。

若一张照片本身横竖方向错误、元数据丢失或倒置，先在照片工具里转正后重新导入，并把它作为可追溯的派生文件。页面的±15°校正不是90°/180°方向识别器，也不做透视校正。

### 5.2 为什么水平投影方差能寻找校正角

文字行摆平后，黑像素更集中在少量行；斜放时分散到更多行。对于候选角θ，先旋转小图，再求水平投影：

```text
Hθ[y]=Σx 1[Bθ(x,y)<128]
μθ=(1/H)Σy Hθ[y]
V(θ)=(1/H)Σy(Hθ[y]−μθ)²
θ*=argmaxθ V(θ)
```

`Hθ` 长度是图高，元素是黑像素数；V单位是“每行计数的平方”。手算比较两个都有8个前景像素的四行投影：`[0,4,4,0]` 均值2、方差4；`[2,2,2,2]` 均值2、方差0。前者更集中，但这种集中也可能来自字形或污渍，所以不能只凭最大值无限旋转。

当前自动策略有明确门槛：

1. 仅在 `autoDeskew=true` 且手动 `correctionAngle=0` 时启用。
2. 前景行框宽须大于高度的2.5倍，避免单个数字的字形主导行方向。
3. 候选用宽度最多300像素的小图搜索，角度为−8°至+8°，步长1°，不做细化。
4. 最佳候选方差须大于0°基线的1.08倍，才接受该角度。
5. 对原处理灰度图双线性旋转，再重新阈值与分割。

例如基线方差100、最佳候选107，则不足108，不校正；候选109则通过此门槛。手动设置2.5°时使用该手动角，不再叠加自动估计。

`correctionAngle` 表示**要对输入施加的旋转角**。第07章的搜索已返回实际试过的最佳旋转候选；本章直接使用它，不再取负。这里 `rotateImage` 的正角为画面逆时针；看到“实际校正−3°”表示顺时针转3°，不是模型测得照片原来为−3°。

图像旋转保持原宽高，边缘可能裁掉笔画；自动搜索又有降采样和整度步长误差。因此HTML同时显示实际角度、校正后灰度图与框，必须一起观察。自动为0°可能是无需旋转，也可能是短串或改善不足，并不表示绝对水平。

2026-09-11修复了共享旋转的中心与边缘取样，并复核了输入归一化。因此当前引擎版本为 `ocr-photo-v2-2026-09-11`，返回值和新评估配置均包含 `pipelineVersion`。下面标注2026-09-08的实测数字属于旧流程，不能直接当作修复后版本的测量。

## 6. 归一化：尺寸、极性、灰度和质心必须与训练一致

### 6.1 为什么不直接把字符框拉伸成28×28

把窄“1”拉成正方形会改变比例；把黑笔画白背景直接除以255，又会得到与模型相反的前景。第17章定义统一契约 `dark-rgba-bbox20-centroid-v1`，训练数字和照片裁剪都调用 `prepareDigit`。

引擎先构造 `inkGray`：二值掩膜判定为背景的位置全部设白，保留位置使用校正后的原灰度。随后按每个框加1像素padding裁剪，再归一化。这样模型仍能看到笔画内灰度，而被阈值误删的笔画已无法恢复。

### 6.2 从强度到固定维度的完整计算

```text
ink(x,y) = [1−(0.299R+0.587G+0.114B)/255]·A/255
有效包围框：ink>0.08 的像素所围成的最小矩形
u(x,y) = ink(x,y)/max(ink)     非空时按峰值缩放
s=20/max(cropW,cropH)
w=max(1,round(cropW·s))，h=max(1,round(cropH·s))
left=floor((28−w)/2)，top=floor((28−h)/2)
```

`ink,u` 均为无量纲强度，背景0，深色笔画接近1。阈值0.08用来找包围框，不是把所有保留像素硬变成1。完全白/透明输入没有有效框，返回 `blank:true`，不会除以0后硬送进模型。

Node实验4从实验3第一框裁剪：原框6×11，加1圈padding得到 **8×13**；重新找出的有效包围框仍为6×11。缩放系数 `20/11≈1.8182`，内容尺寸 `w=11,h=20`，初始 `left=8,top=4`。它没有变成28×28的实心宽矩形，原来的上下断口也仍影响强度分布。

双线性插值根据像素中心映射取样。一般四角值 `q00,q10,q01,q11` 与小数位置 `dx,dy` 给出：

```text
q=(1−dx)(1−dy)q00 + dx(1−dy)q10
 +(1−dx)dyq01 + dx·dyq11
```

例如四角 `[1,0;0,0]`，在 `dx=dy=0.5` 时输出0.25；这就是灰度边缘，不能把展示图上的浅灰都当作噪点。代码把取样中心限制在有效框边缘内，再调用 `sampleBilinear`。

### 6.3 用灰度质量中心调整位置

尺寸一致仍可能“重心偏左”。对28×28画布上强度u计算：

```text
M=Σu(x,y)，cx=Σx·u/M，cy=Σy·u/M
dx=round(13.5−cx)，dy=round(13.5−cy)
```

13.5是坐标0–27的几何中心。实际平移会再限制在可用留白范围，避免将内容移出画布。假设 `M=100,Σxu=1200,Σyu=1400`，则质心 `(12,14)`，JavaScript取整得到 `(dx,dy)=(2,0)`，前提是留白允许；整数平移后不保证质心精确等于13.5。

受控6×11对称断笔块缩成11×20后，初始横向几何中心为13，纵向13.5；有限取整会将横向中心移到附近整数位置。这种约定必须在训练和推理中一致，不要随意改成28为中心或强行“精确居中”。

最终 `pixels` 是长度784的 `Float32Array`；构建张量形状是 `[1,28,28,1]`，按 NHWC 排列，最后1表示灰度通道。`imageData` 是便于观看的**黑笔画白背景**RGBA图：显示黑色对应模型强度1，显示白色对应强度0。

默认 `contentSize=20`、阈值0.08；API允许内容最长边1–24、阈值在0与1之间。这些是模型输入约定，改变它们就是改变实验配置，不能期待只因仍是784维就与旧权重匹配。弱笔画若全低于阈值，会直接判空；过大内容会减少平移留白；大污渍会把包围框拉宽，压缩真正数字。

## 7. 真实 CNN 输出：从784个强度到一个字符

### 7.1 模型实际做了什么

页面与Node加载的是第17章自行训练的 `model/model.json` 与 `weights.bin`。当前训练报告标识为 `ocr-mnist-cnn-v1-9c7b0b8e8224`，不是随机权重，也不是根据样例答案返回固定串。

实际网络是两层带步幅卷积后接全连接，当前结构中没有池化层：

| 层 | 计算 | 输出形状，N表示批量 | 参数数 |
|---|---|---|---:|
| 输入 | 单通道28×28 | `[N,28,28,1]` | 0 |
| Conv1+ReLU | 5×5，stride2，valid，8通道 | `[N,12,12,8]` | `(5×5×1+1)×8=208` |
| Conv2+ReLU | 3×3，stride2，valid，16通道 | `[N,5,5,16]` | `(3×3×8+1)×16=1168` |
| Flatten | 展平5×5×16 | `[N,400]` | 0 |
| Dense+ReLU | 400→32 | `[N,32]` | `400×32+32=12832` |
| Dropout | 训练丢弃率0.15；预测不随机丢弃 | `[N,32]` | 0 |
| Dense+softmax | 32→10 | `[N,10]` | `32×10+10=330` |

空间维度公式是 `floor((L−kernel)/stride)+1`：第一层 `(28−5)/2` 向下取整再加1得12，第二层得5；总参数 **14,538**。第25章逐框调用，所以这里的N每次为1，而不是照片数字串长度。

对每个区域，最后10个得分按0–9排列。softmax定义为：

```text
pc=exp(zc−max(z))/Σj exp(zj−max(z))
label=argmaxc pc，score=maxc pc
```

减去最大logit不改变比例，并避免指数溢出。假设某行真实模型输出的形式是 `[0.01,0.02,0.80,0.03,0.02,0.02,0.01,0.03,0.04,0.02]`，和为1，argmax为类别2，最高得分0.80；这是**解释排序的手算向量**，不是本仓库某张照片的实测输出。实测分数看Node实验5的表格及页面字符卡片，鼠标停留可查看前三候选。

共享 `recognizePhoto` 接口只要求回调给出10个有限、非负得分，不强制其和为1；是当前CNN末层softmax赋予了概率分布形式。换成其他分类器时不能假定任意分数都可以显示为百分比。

### 7.2 confidence 不等于 accuracy

最高softmax分数描述模型对**当前裁剪**的判断。假设一批10个样本都显示0.99，但对照答案只对了8个：实际准确率是 `8/10=80%`，平均得分仍为99%。错误分割的“半个8”也可能得到很高的3分数；分数没有把“少切了一个框”的风险计算进去。

置信度需要在有代表性的独立数据上检验是否校准；现代网络可出现高分但错误，见[置信度校准原论文](https://proceedings.mlr.press/v70/guo17a.html)。本引擎未实施概率校准，也没有将各字符分数相乘后宣称整串正确概率。

第17章报告的标准单数字测试为 **9769/10000=97.69%**，训练55,000、验证5,000、5轮，模型按验证交叉熵选择。即使做“每位正确概率0.9769且相互独立”的理想化假设，6位全对也只能写为 `0.9769⁶≈86.92%`；现实还包含域差异和分割错误，不能把这个推算当合成行或实拍成绩。真实来源是[训练报告](../17-cnn-classifier/model/training-report.json)。

### 7.3 字符串拼接与资源释放

每框输出标签字符串，代码按顺序 `join('')`。若标签依次为 `['0','0','1','1','0']`，结果就是 `'00110'`。转Number会丢前导零，Set去重会丢重复数字，CTC折叠会错误地把相邻两个1合并；这三种操作均不属于本引擎。

浏览器使用 `tf.loadLayersModel` 加载模型并检查输入28×28×1、输出10类；通过元数据中的SHA-256核验权重。加载行为与模型/权重文件关系见 [TensorFlow.js 保存加载文档](https://www.tensorflow.org/js/guide/save_load)。Node通过第17章 `model-io.js` 读取本地权重、核验哈希，再交给 `tf.io.fromMemory`，不要求另装 `tfjs-node`。

每次预测的临时输入/输出张量放在 `tf.tidy` 中，内部同步读取到普通数组后返回；不要把尚未解析的Promise塞进这个同步作用域。模型在多张照片间复用，页面重新加载时释放旧模型，Node在finally中释放。得分、浮点尾数与耗时会随CPU/WebGL、图像解码和首次预热有小差异；“固定种子”不意味着跨后端逐位相同。

## 8. 方法路线比较：哪些课程知识进入本版引擎

| 路线 | 输入和输出 | 本任务中的收益 | 局限/本版位置 |
|---|---|---|---|
| 模板/KNN，12–13章 | 单字特征→类别 | 能观察距离、模板和邻居 | 对齐与模板覆盖敏感；没有替代当前CNN |
| 连通域过滤+投影+CNN | 有间隔单行→框→类别串 | 能把每个错误定位到框与归一化图 | 粘连、重叠、多行不可靠；本版实际路线 |
| CRNN+CTC，18–20章 | 整行特征序列→无逐字框的数字串 | 研究显式分割成为瓶颈后的替代方案 | 需要整行训练与解码；本版未接入 |
| EAST/DBNet，22章 | 图片→文本区域 | 研究复杂背景和多区域定位 | 检测本身不完成数字识别；本版未接入 |
| Transformer OCR，21/23章 | 图像特征与序列建模→文本 | 学习注意力、位置编码、现代识别架构 | 数据和计算要求不同；本版未借用公开模型替代自主训练 |

选择哪条路线应看独立开发照片的失败归因。如果十次失败中八次是框数量错误，单纯增加CNN容量可能没有解决主要问题；如果每个框和归一化都清楚、仍经常把9分成4，才更接近分类器及数据覆盖问题。这个“8/10”是决策算例，不是本项目实拍统计。

### 9.2 核心API契约

| API | 输入 | 输出与对应教学点 |
|---|---|---|
| `validateImage(image)` | `{width,height,data}`，RGBA长度4WH | 无返回数据；非法形状/过大图抛错 |
| `flattenImage(image)` | RGBA | 白底合成后的灰度RGBA；不改原图 |
| `adaptiveMeanFast(gray,k,C)` | 灰度RGBA、奇数窗口、有限偏移 | 同尺寸二值RGBA；只把R作为灰度使用 |
| `foregroundBounds(binary)` | 黑白图 | `{x,y,width,height,count}` 或 `null` |
| `cropImage(image,box,padding)` | 图、框、可选留边 | 裁剪图；越界范围截到图内；空裁剪抛错 |
| `segmentDigits(binary,options)` | 二值图、minArea/mergeGap | `{boxes,binary,bounds,warnings}`，binary是清理结果 |
| `preprocessPhoto(image,options)` | RGBA和处理参数 | `{gray,binary,inkGray,boxes,bounds,correctionAngle,warnings}` |
| `recognizePhoto(image,{prepareDigit,predict,...options})` | 图与两个函数；不传答案 | Promise，含预处理字段与`characters,text,status,elapsedMs` |

`characters` 每项包括 `box`、字符标签 `label`、最高得分 `score`、按得分排序的全部10个 `candidates`，以及用于展示的28×28 `normalized`。回调 `predict(pixels,index)` 接收784个强度和从0开始的框索引，可异步返回得分。当前页面使用真实CNN，同步取数组后交给引擎。

| options参数 | 共享默认值 | 范围与注意点 |
|---|---|---|
| `thresholdMethod` | `'otsu'` | `'otsu'/'adaptive'/'fixed'`；未知方法报错 |
| `threshold` | 128 | 固定模式，有限数值0–256；页面固定128 |
| `blockSize`、`offset` | 41、8 | 自适应模式，奇数≥3、有限数值；页面使用默认值 |
| `denoise` | 未设置即关闭 | 启用时执行3×3中值 |
| `correctionAngle` | 0 | 有限值，−15°至15°；页面步长0.5° |
| `autoDeskew` | 未设置即关闭 | 页面及Node实图实验主动设为true；不覆盖非零手动角 |
| `minArea` | `max(3,round(Amax×0.007))` | 有限数值≥1；对连通域面积过滤 |
| `mergeGap` | `max(1,round(h×0.025))` | 非负整数；只有空白列数严格大于它才分框 |

`preprocessingId` 是页面记录的第17章归一化版本，不是 `preprocessPhoto` 的算法开关。记录版本不能自动保证文件没变：复现实验还应保存对应共享实现和模型产物。

### 10.2 七个Node实验应观察什么

| 实验 | 默认输入/配置 | 可核对输出与结论 |
|---|---|---|
| 1 alpha | 透明黑、A=128半透明黑 | 灰度255、127 |

### 10.3 HTML建议的四轮观察

1. **基线流程。** 等模型“已就绪”，点“加载手写样例”，开始识别。按原图→阈值图→框→归一化卡片→完整串检查，确认一框对应一位。
2. **方法对照。** 保存基线首次结果，换开发实验轮次，选择局部均值后重新识别；比较框和灰度边缘。光照均匀的样例可能两者都对，不能据此宣布一种方法更好。
3. **输入边界。** 导入一张白图，看空结果；导入实际保存的横向照片，观察自动角度，再在新开发轮次尝试手动角。页面没有手绘板或自动收群图功能。
4. **评估交接。** 根据纸面录入正确数字串，点“核对”，再保存本轮首次结果，去第26章查看。答案只参与比较，不改变字符框和预测。

特别注意：页面“核对”比较当前最新结果，**“保存本轮首次结果”保存这张输入本轮第一次运行的结果**。同轮改参数重试后，当前画面可能已正确，保存的却仍是第一次错误结果，这是保留实验事实。做A/B对照时先保存A，修改实验轮次，再执行并保存B；同图同轮重复保存会被拒绝。

## 11. 排障：根据最早出错的中间状态定位

| 现象 | 优先检查 | 处理和记录方式 |

| 校正越调越歪 | 使用的是校正角还是拍摄角 | 回到0，比较灰度图；不对搜索结果再次取负 |
| 方向横竖错 | 图片元数据或原图朝向 | 在图片工具转正并保留原图；±15°不能解决横竖方向 |
| Node提示建议安装native后端 | 是否只是TensorFlow.js性能提示 | 默认纯JS CPU可运行；提示本身不是实验失败 |
| 保存后和当前画面不同 | 是否同轮重试 | 去第26章看首次预测；新配置使用新轮次 |
| 评估页没有刚存的记录 | 地址、端口、浏览器、是否刷新 | localStorage按来源隔离；使用同一地址，刷新评估页 |
| 文件打不开/超大小 | 格式、损坏、20 MiB限制 | 页面清除旧输入，不会自动生成一条可保存识别记录；另行记入接收台账 |

最后一项意味着“所有收到的文件”不能只靠评估页数量反推：读取失败发生在推理前，需按第26章流程额外保留排除原因。普通识别错误和合法输入的空结果则应留在有效分母。

## 14. 分享要点与下一章联系

可自行组织成三段讲解：先用透明黑和`t=0`说明接口约定会造成整条流程失效；再用断笔矩形与28×28卡片展示分割、归一化怎样改变模型实际看到的东西；最后用真实`001208`样例讲清“模型得分、一次成功、独立数据集成绩”三者区别。

值得让听众现场手算的是局部窗口25−8=17、断笔过滤的面积门槛、两层卷积尺寸，以及前导零的字符串拼接。一次失败时先问“最早哪张中间图不合理”，不要从最终错误标签倒推所有模块都坏了。

继续到[第26章验证](../26-validation/README.md)：为每张照片建立独立答案、按字符总数汇总CER、保留失败和首次结果，并区分标准单数字、合成行和真实照片。
